# PostgreSQL и MCP для персонального ассистента

Текущий этап: три MCP-инструмента подключены через FastMCP 4.1.3.
Реализованы stdio и Streamable HTTP. Redis 8.2.10 запущен через Docker для памяти
диалога; Python-клиент redis 8.1.0. PostgreSQL работает локально вне Docker.
Интеграция с настоящим ботом/LLM команды ещё предстоит.

## Что где находится

- `app/config.py` читает настройки, не печатает пароль.
- `app/db/connection.py` открывает соединение через psycopg 3.
- `app/db/__main__.py` проверяет подключение и применяет SQL.
- `sql/001_create_events.sql` создаёт таблицу и ограничения.
- `app/events.py` содержит `EventService`: валидацию, SQL и сериализацию ответов.
- `app/mcp_server.py` регистрирует три MCP-инструмента и запускает сервер.
- `app/check_mcp.py` — рабочий пример MCP-клиента без записи событий.
- `app/memory.py` — история диалога и событие, ожидающее подтверждения.
- `app/confirmation.py` — сохранение подтверждённого предложения через MCP.
- `compose.yaml` — отдельный локальный Redis; PostgreSQL не затрагивает.
- `docs/AGENT_INTEGRATION.md` — интерфейс и порядок подключения для команды.
- `docs/STATUS.md` — что готово, что проверено, какие пробелы остаются.
- `tests/test_events.py` проверяет неверные входные данные без БД.
- `tests/test_postgres.py` проверяет реальный PostgreSQL.
- `.env.example` — образец локальных настроек без пароля.

## Подготовка в PyCharm / PowerShell

Рабочая папка — корень проекта. В PyCharm выберите существующий интерпретатор
`.venv\Scripts\python.exe`. Если окружение ещё не создано:

```powershell
py -3.13 -m venv .venv
```

Активация окружения не обязательна: команды ниже вызывают его Python напрямую.

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.lock.txt
Copy-Item .env.example .env
```

Копируйте образец только если `.env` ещё нет. Откройте `.env` в PyCharm
и заполните `PGPASSWORD` своим локальным паролем PostgreSQL. Не отправляйте
пароль в чат. Системные переменные окружения имеют приоритет над `.env`.
Если файл блокировки ещё не подготовлен, используйте `requirements.txt`.

## Отдельная база данных

Для проекта используем `assistant_mvp`. Если базы ещё нет, в pgAdmin откройте
Query Tool базы `postgres`, включите Auto-commit и выполните:

```sql
CREATE DATABASE assistant_mvp;
```

Команда выполняется один раз, вне транзакции. Существующие базы не удаляем.
Для локального MVP можно использовать установленную роль `postgres`;
перед общим развёртыванием создадим отдельную роль с ограниченными правами.
Не применяйте схему к базе с чужими таблицами.

```powershell
.\.venv\Scripts\python.exe -m app.db check
.\.venv\Scripts\python.exe -m app.db init
.\.venv\Scripts\python.exe -m app.db check
```

`init` создаёт `public.events` в одной транзакции. При ошибке изменения
откатываются. Повторный `init` завершается ошибкой существующей таблицы;
он не удаляет и не перестраивает данные. Соединения закрываются после команды.
Эти команды завершаются сами. Запуск отдельного MCP-сервера описан ниже.

## Контракт MCP-инструментов

- `create_event(user_id, event_type, name, datetime, description="", idempotency_key=None)`.
- `get_event(user_id, start_time, end_time, event_type=None, limit=100, offset=0)`.
- `get_event_by_query(user_id, text, start_time=None, end_time=None, limit=100, offset=0)`.

Параметры передаются по именам. Неопределённый параметр `list` заменён
на `limit` и `offset` после обсуждения. Все ID пользователей — непустые строки.
Тип события: `task`, `reminder`, `meeting`. Название: 1–200 символов после
удаления пробелов по краям; описание: до 10 000 символов.
`limit`: 1–100; `offset`: целое неотрицательное число.

Дата приходит в ISO 8601 с часовым смещением, например
`2026-10-25T10:00:00+03:00`; без смещения отклоняется. БД хранит момент
в `timestamptz`, ответы будут в UTC. Часовой пояс пользователя задаёт агент;
он же переводит «завтра» в точные границы. Интервал `[start_time, end_time)`:
начало включено, конец исключён; начало должно быть раньше конца.
Для чтения сортируем по `event_at`, затем `id`.

Создание: `{"event": {...}, "created": true}`. Повтор с тем же ключом
и теми же данными возвращает существующую запись с `created: false`.
Другие данные с тем же ключом — конфликт. Без ключа повторы могут создавать
отдельные события. Чтение: `{"items": [...], "has_more": false}`;
пустая выдача — `items: []`. Ошибки станут ошибками MCP-вызова.

Фильтр по user_id обеспечивает выборку указанного пользователя, но не
авторизацию. Доверенный backend должен проверять, чей ID передаёт агент.
Предоставлены stdio и Streamable HTTP; совместимость именно с клиентом команды
нужно проверить при интеграции. В нашей проверке используется FastMCP Client 4.1.3.
Доставка напоминаний и изменение статусов не входят в эти три инструмента.

## Использование без MCP

```python
from app.config import Settings
from app.events import EventService

events = EventService(Settings.load())
result = events.create_event(
    user_id="demo:fictional-user",
    event_type="task",
    name="Подготовить презентацию",
    description="Собрать материалы для команды",
    datetime="2030-01-02T10:00:00+03:00",
    idempotency_key="demo-operation-001",
)
print(result)
```

Пример создаёт настоящую запись с вымышленными данными. Не вызывайте создание
до подтверждения пользователя в агенте. Один ключ соответствует одной операции,
а не всему диалогу. Передавайте тот же ключ при повторной попытке после сбоя.

Функции принимают ISO-строки либо timezone-aware Python datetime. Текстовые
поля обрезаются по краям; сравнение повторной операции выполняется после
нормализации текста и перевода времени в UTC. idempotency_key в ответы не входит.
Ошибки: `ValidationError`, `ConflictError`, `StorageError`. Ошибки хранилища
не содержат пароль или исходное сообщение PostgreSQL. Даже при ошибке ответа
на COMMIT запись могла сохраниться: повторяйте запрос с тем же ключом.

Русский поиск использует `plainto_tsquery('russian', text)` и название вместе
с описанием. Все значимые слова запроса должны присутствовать в документе;
операторы в тексте запроса не интерпретируются как SQL или поисковая логика.
Формы слов учитываются, но опечатки, подстроки и смысловая близость — нет.
Запрос из одних стоп-слов возвращает пустой список. Выдача сортируется по
времени события и ID. Индексы добавляются миграцией 002; см. INDEXES.md.
При параллельном добавлении событий пагинация через offset может сдвигаться;
она не гарантирует неизменный снимок между вызовами.

## Проверки

Без PostgreSQL:

```powershell
.\.venv\Scripts\python.exe -m unittest tests.test_events -v
```

С реальными PostgreSQL и Redis из локального `.env` (Redis должен быть запущен):

```powershell
$env:ASSISTANT_RUN_DB_TESTS='1'
$env:ASSISTANT_RUN_REDIS_TESTS='1'
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
Remove-Item Env:ASSISTANT_RUN_DB_TESTS
Remove-Item Env:ASSISTANT_RUN_REDIS_TESTS
```

Интеграционные тесты создают вымышленные записи в настроенной проектной БД
для случайных user_id с префиксом `test:`. Они намеренно остаются после запуска:
тесты не выполняют DELETE, DROP или TRUNCATE. Каждый запуск использует новые ID.
Проверяются типы событий, русские название и описание, временные границы,
изоляция пользователей, пагинация, повторные и конкурентные операции,
ошибка подключения и чтение из нового Python-процесса. Это проверка сохранения
между процессами приложения, а не перезапуск самой службы PostgreSQL.
Без явного флага интеграционные тесты пропускаются.
`tests/test_mcp.py` дополнительно проверяет схему инструментов, неверные типы,
ошибку хранилища и полноценные MCP-вызовы в отдельных процессах через stdio
и Streamable HTTP. В сценариях с реальной БД создаются вымышленные события.
Сообщения Error/Warning при проверке неверных запросов ожидаемы;
результат всей проверки — итоговое `OK` или `FAILED`.

## Запуск MCP

Для локального backend агента можно использовать stdio: клиент сам запускает
процесс сервера и останавливает при отключении. Быстрая проверка без записи:

```powershell
.\.venv\Scripts\python.exe -m app.check_mcp
```

Настройка клиента, умеющего запускать MCP-процесс: команда — абсолютный путь
к `.venv\Scripts\python.exe`, аргументы — `-m app.mcp_server`, рабочая папка —
корень проекта. При ручном запуске stdio-сервер ждёт MCP-запросы, обычную
строку в терминале вводить не нужно. Служебные сообщения идут в stderr,
stdout оставлен для протокола.

Для HTTP запустите в терминале PyCharm из корня проекта:

```powershell
.\.venv\Scripts\python.exe -m app.mcp_server --transport http
```

MCP endpoint: `http://127.0.0.1:8001/mcp`, транспорт Streamable HTTP.
Остановка — Ctrl+C. Для другого порта добавьте `--port 8002`.
Во втором терминале проверка запущенного HTTP-сервера:

```powershell
.\.venv\Scripts\python.exe -m app.check_mcp --transport http
```

HTTP пока слушает только localhost и не имеет авторизации. На другом компьютере
127.0.0.1 указывает на него самого, а не на этот сервер. Перед доступом по сети
подготовим авторизацию и развёртывание. Не открывайте текущий endpoint в интернет.
Подсказки MCP требуют подтверждения пользователя, но сам сервер не проверяет
историю диалога: это обязанность агента. Память Redis и связка сохранения готовы;
разработчик агента должен включить их в свой обработчик сообщений.

Пример для разработчика агента, когда HTTP-сервер уже запущен:

```python
from fastmcp import Client
from fastmcp.client.transports import StreamableHttpTransport
import httpx2

async def read_events(trusted_user_id: str):
    transport = StreamableHttpTransport(
        "http://127.0.0.1:8001/mcp",
        # Локальный запрос не должен идти через системный прокси.
        httpx_client_factory=lambda **kw: httpx2.AsyncClient(trust_env=False, **kw),
    )
    async with Client(transport, timeout=20) as client:
        result = await client.call_tool("get_event", {
            "user_id": trusted_user_id,
            "start_time": "2030-01-02T00:00:00+03:00",
            "end_time": "2030-01-03T00:00:00+03:00",
        })
        return result.structured_content
```

По умолчанию клиент поднимает исключение на ошибку инструмента. Если требуется
обработать MCP-ответ вручную, передайте `raise_on_error=False`, проверьте
`result.is_error`, и только при успехе читайте `result.structured_content`.
Ошибки бизнес-логики помечаются VALIDATION_ERROR, CONFLICT или STORAGE_ERROR.
Ошибка сохранения не подтверждает отсутствие записи: повторите создание
с тем же idempotency_key. Валидация схемы выполняется строго: строка "10"
и boolean не принимаются вместо целого limit.

Документация API: https://gofastmcp.com/servers/tools и
https://gofastmcp.com/clients/transports . Версии установленных зависимостей
зафиксированы в requirements.lock.txt для текущего Windows/Python 3.13.
Linux-зависимости зафиксированы отдельно в requirements.linux.lock.txt; полный запуск описан в корневом README.

## Redis: запуск и назначение

Docker Desktop должен работать. Из корня проекта:

```powershell
docker compose up -d --wait redis
.\.venv\Scripts\python.exe -m app.memory
docker compose ps
```

Проверка `app.memory` выполняет только PING. Настройки Redis имеют рабочие локальные
значения по умолчанию: существующий `.env` переписывать не нужно. Для изменения
настроек скопируйте соответствующие строки из `.env.example` вручную.
`REDIS_URL=redis://127.0.0.1:6379/0`; если меняете порт, согласованно измените
`REDIS_BIND_PORT` и порт в `REDIS_URL`.

Остановка только этого Redis:

```powershell
docker compose stop redis
```

Повторный запуск — `docker compose up -d --wait redis`. После остановки/перезапуска
контекст теряется: запись на диск намеренно выключена. В сохранённых событиях
PostgreSQL ничего не меняется. Контейнер доступен только на localhost и без пароля;
перед сетевым развёртыванием понадобятся отдельные настройки доступа.
Перезапуск Docker Desktop сам по себе может запускать этот контейнер благодаря
политике `unless-stopped`, если он не был остановлен вручную.

История до 10 сообщений пользователя и ассистента, TTL 15 минут после последней
активности. Отдельно — ожидающее подтверждения событие и idempotency_key.
При исправлении деталей агент повторно запрашивает подтверждение. При потере
контекста агент просит повторить детали; события остаются в PostgreSQL.
Агент управляет подтверждением, хранилище не может проверить согласие пользователя.
ASR передаёт `text`, `engine`, `audio_sec`, `latency_ms`; аудио наша часть не хранит.

TTL обновляется записью сообщения или нового предложения, чтение его не продлевает.
Ограничение — 10 сообщений всего, а не 10 пар. После подтверждения предложение
удаляется только при совпадении ключа операции; история доживает до своего TTL.
При недоступном Redis выдаётся ошибка, а не пустой контекст: агент не должен
угадывать, что подтверждал пользователь. MCP и PostgreSQL могут работать отдельно
от Redis для прямых запросов. Память предоставляет Python-интерфейс backend,
новые MCP-инструменты не добавлялись.

Redis-тесты из `tests/test_memory.py` используют собственные случайные префиксы,
TTL и вымышленные данные; FLUSHDB/FLUSHALL не выполняются. Проверяются ограничение
истории, изоляция, ASR, истечение и обновление TTL, конкурентные добавления,
защита нового предложения от старого ответа, ошибки Redis и полный сценарий
подтверждения через настоящий MCP-процесс. Истечение/потеря контекста проверены;
перезапуск контейнера для имитации потери в тестах не выполняется.
