# Индексы и воспроизводимая проверка

Миграция sql/002_event_indexes.sql добавляет ровно три индекса:

| Индекс | Зачем |
| --- | --- |
| events_user_time_idx (user_id, event_at, id) | События пользователя за период; порядок времени/ID |
| events_user_type_time_idx (user_id, event_type, event_at, id) | Та же выдача с равенством event_type |
| events_search_gin_idx | Русский полнотекстовый поиск одновременно по названию и описанию |

В B-tree сначала идут поля с равенством, затем диапазон. Индекс с event_type
не заменяет индекс без него: для всех типов между user_id и event_at остаётся
неограниченный столбец. id согласует стабильную сортировку одинакового времени.
Планировщик может выбрать Bitmap Scan и отдельную сортировку, а не Index Scan;
это нормальное решение по оценке стоимости.

GIN использует точное выражение to_tsvector('russian', name || ' ' || description),
совпадающее с запросом. Словоформы поддерживаются, подстроки/опечатки/семантика — нет.
Запрос из одних стоп-слов даёт пустую выдачу. Полнотекстовый поиск сам по себе
работал и до индекса; GIN ускоряет поиск кандидатов. Фильтр user_id остаётся в SQL.

Цена: дополнительное место и обслуживание трёх индексов при вставках/изменении
полей. На искусственных 100000 строках два B-tree заняли примерно 5.6 и 6.5 MiB,
GIN — 5.8 MiB. Это не оценка размера на ваших будущих данных.
Нет отдельных индексов на каждое поле, статус или created_at: под них сейчас
нет согласованных запросов. Первичный ключ и уникальность операции остаются.

## Фактический локальный эксперимент

PostgreSQL 17.6, временная таблица, 100000 вымышленных событий, 100 пользователей,
три прогона каждого SELECT до/после индексов. Первичный ключ и уникальный индекс
существовали уже в исходном варианте. Настройки планировщика не принуждались.

| Сценарий | До, медиана ms | После, медиана ms |
| --- | ---: | ---: |
| Период пользователя | 0.554 | 0.091 |
| Период + тип | 0.574 | 0.037 |
| Русский поиск | 9.334 | 0.171 |

Это синтетические замеры с прогретым кешем, а не SLA и не производительность
реального проекта. Данные и размеры искусственны; повторный запуск даст другие
значения. Для поискового запроса выбран BitmapAnd существующего индекса user_id
и нового GIN. Для периодов использованы соответствующие новые B-tree.
Полные EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) сохранены в
reports/index_plans.local.json.

## Повторение в Docker

После старта полного стека:

```sh
docker compose --env-file .env.docker -f compose.full.yaml --profile tools run --rm benchmark
```

Отчёт появится в docs/reports/index_plans.json. Скрипт создаёт только временную
таблицу и автоматически освобождает её при завершении транзакции; настоящие
events и пользовательские записи не меняются. Принудительные seqscan/indexscan
не используются. Для маленькой настоящей events последовательное чтение может
быть дешевле индекса — наличие индекса не обязывает PostgreSQL использовать его.

Миграции для MVP создают индексы в транзакции, с ограничением ожидания блокировки.
На большой работающей БД нужна отдельная процедура CREATE INDEX CONCURRENTLY
с учётом её ограничений; текущую миграцию не выдаём за готовую онлайн-миграцию.

Основание: [многоколоночные индексы PostgreSQL](https://www.postgresql.org/docs/17/indexes-multicolumn.html),
[GIN для полнотекстового поиска](https://www.postgresql.org/docs/17/textsearch-indexes.html).
