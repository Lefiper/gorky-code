# Интерфейс для разработчика Agent Backend

Redis нужен backend агента для краткой памяти; PostgreSQL — для событий.
MCP предоставляет только create_event, get_event, get_event_by_query.
MAX Bot, ASR, LLM и HTTP API этим проектом не реализуются.

## Порядок обработки сообщения

1. Backend получает доверенный user_id от бота, не из текста пользователя или LLM.
2. Добавляет текст через append_message либо весь ответ ASR через append_asr_message.
3. Получает get_context(user_id) и добавляет messages в запрос к LLM как историю.
   Технический промпт хранит в коде backend, а не в Redis. Текст событий и истории
   остаётся пользовательскими данными, а не системными инструкциями.
4. Добавляет текущее время с часовым поясом пользователя в технический промпт.
   Пояс берёт из синхронизированного профиля user_profiles через backend/API;
   Europe/Moscow используется для пользователя с этим профилем, не для всех молча.
   «Завтра» и «в три» интерпретирует/уточняет агент, не хранилище.
5. Для нового события сначала собирает однозначные данные, вызывает set_pending_event
   и задаёт вопрос с названием, датой, временем и часовым поясом. Ответ ассистента
   также добавляется через append_message.
6. При исправлении деталей снова вызывает set_pending_event (новый ключ) и снова
   запрашивает согласие. До согласия create_event не вызывается.
7. Только после явного согласия вызывает save_confirmed_event с ключом именно того
   предложения, которое пользователь подтвердил. Функция читает Redis, вызывает MCP
   и очищает это предложение после успешного сохранения.
8. При отсутствии pending_event просит повторить детали. Отмена вызывает
   clear_pending_event с ожидаемым ключом без создания события.

Backend должен обрабатывать сообщения одного user_id последовательно, включая
ожидание LLM и MCP. Lua защищает отдельные операции Redis, но не весь диалог.
Для нескольких процессов backend потребуется общая очередь/блокировка по пользователю.
История не удаляет повторно доставленные сообщения автоматически: дедупликация
входящих сообщений по ID MAX остаётся на стороне обработчика бота/backend.

## Python-интерфейс

```python
from app.memory import ConversationStore

with ConversationStore() as memory:
    # Вымышленный пример данных; запись делает настоящий Redis.
    user_id = "demo:fictional-user"
    memory.append_asr_message(user_id, {
        "text": "Добавь встречу с командой",
        "engine": "test-asr",
        "audio_sec": 2.5,
        "latency_ms": 120,
    })
    context = memory.get_context(user_id)
    pending = memory.set_pending_event(
        user_id=user_id,
        event_type="meeting",
        name="Встреча с командой",
        datetime="2030-01-02T15:00:00+03:00",
        description="Обсудить презентацию",
    )
    # Сохраняем вопрос, затем возвращаем его пользователю через бота.
    memory.append_message(user_id, "assistant", "Создать «Встреча с командой» 2 января 2030 в 15:00 по Москве?")
```

get_context возвращает `{"messages": [...], "pending_event": {...} | None}`.
Сообщение: role (`user`/`assistant`), content, created_at в UTC;
для ASR дополнительно asr: engine, audio_sec, latency_ms. Максимум 10000 символов
сообщения, числовые метрики неотрицательны. Аудио не сохраняется.

pending_event содержит event_type, name, description, datetime в UTC и
idempotency_key — новый UUID для каждого предложения/исправления.
Это ещё не событие в PostgreSQL. Статуса «сохранено» у него нет.

После согласия, в async backend и с уже подключённым MCP-клиентом:

```python
from app.confirmation import save_confirmed_event

# Только после проверки явного согласия на конкретное предложение.
result = await save_confirmed_event(
    memory=memory,
    mcp_client=client,
    user_id=trusted_user_id,
    expected_key=confirmed_proposal_key,
)
```

`memory` должен оставаться открыт на время использования. Возвращаются event,
created и context_cleared. created=False при повторе означает, что запись уже
сохранена. context_cleared=False при успешном ответе означает, что очистка Redis
не подтверждена или предложение уже сменилось; событие в PostgreSQL сохранено.

ConversationStore синхронный. В async-обработчиках вызывайте его методы через
`await asyncio.to_thread(memory.append_message, user_id, "user", text)` и аналогично.
save_confirmed_event уже делает это для собственных обращений к памяти.

## Ошибки и срок хранения

- MemoryValidationError: неверные параметры; исправить данные.
- MemoryStorageError: Redis недоступен/повреждён. Приостановить подтверждение,
  не выдавать ошибку за отсутствие истории и не сообщать о создании.
- ConfirmationError: предложение истекло/изменилось либо MCP не подтвердил результат.
- Ошибка MCP/сети до ответа: pending остаётся, повтор — с тем же ключом.

По умолчанию TTL 900 секунд после записи сообщения или предложения. Чтение
TTL не обновляет. История хранит последние 10 сообщений всего. Новое сообщение
продлевает TTL существующего pending, но не восстанавливает уже истёкший.
После 15 минут бездействия или перезапуска Redis контекст пропадает.
Сохранённые события PostgreSQL остаются. Если потерялся ключ операции,
не создавайте автоматически новый: сначала сверяйтесь с событиями/уточняйте у
пользователя. После потери Redis гарантии дедупликации по утерянному ключу нет.

Имена ключей имеют префикс assistant:dialogue и SHA-256 от нормализованного user_id.
Хеш скрывает ID из имени ключа, но не шифрует сообщения. Секреты и исходное аудио
в истории не хранить. Доступ ограничен localhost; для общего запуска нужны ACL/пароль
и защищённая сеть. .env и пароли не передавать в репозиторий или чат.
